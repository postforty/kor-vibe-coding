# 2부: 백발백중 쥐 잡기 - 확률을 지배하는 프롬프트 기술 (45분)

---

## 🎯 기본기: 찰떡같이 알아듣는 3가지 필수 기술

### 🎭 [역할 부여] 페르소나 (Persona)
소에게 최면 걸기 ("너는 지금부터 최고의 쥐잡기 전문가 고양이야")

#### 📝 [예제 적용] 페르소나에 따른 결과 차이 체감
```text
너는 백설공주 이야기 속의 거울이야. 그 캐릭터에 부합하게 답변해줘.
- 세상에서 누가 제일 아름답니?

너는 배트맨에 나오는 조커야. 악당 캐릭터에 맞게 답변해줘.
- 세상에서 누가 제일 아름답니?
```

---

### 🗣️ [시범 보이기] 퓨샷 프롬프팅 (Few-shot)
"쥐는 이렇게 생겼고 이렇게 잡는거야"라고 예시를 직접 학습시키기

#### 📝 [예제 적용] 제로샷 vs 퓨샷 비교
```text
[제로샷] 아무 예시 없이 질문하기
너는 유치원 학생이야. 유치원생처럼 답변해줘.
- 오리

[퓨샷] 여러 가지 예시로 패턴 학습시키기
너는 유치원 학생이야. 유치원생처럼 답변해줘.
선생님: 참새
유치원생: 짹짹
선생님: 강아지
유치원생: 멍멍
선생님: 고양이
유치원생: 냐옹
선생님: 오리
유치원생: 
```

### 🔗 [사고의 사슬] CoT (Chain of Thought)
"단계별로 생각하라"는 주문을 넘어, **성급하게 코드부터 고치려는 AI에게 브레이크를 거는 기술**입니다.

> [!NOTE]
> 💡 **Q. 요즘 AI는 그냥 로그인 버튼 고쳐달라고 해도 알아서 잘 고쳐주지 않나요?**  
> 맞습니다. 최신 모델은 그냥 부탁해도 그럴듯한 코드를 바로 완성해 줍니다.  
> 하지만 AI는 가장 흔한 원인 하나를 멋대로 단정하고 멀쩡한 기존 코드를 뜯어고치거나, 부작용(Side Effect)을 무시하는 고질적인 습관이 있습니다.  
> 그래서 실무에서는 "**코드부터 짜지 말고, 원인과 영향도부터 따져봐**"라고 사고의 순서를 강제하는 안전장치가 반드시 필요합니다.

#### 📝 [실무 시연] 성급한 코딩을 막는 한 줄 안전장치
```text
웹사이트 로그인 버튼이 간헐적으로 안 눌리는 버그가 있어.
코드부터 짜지 말고, [원인 분석 ➔ 부작용 검토 ➔ 해결 코드] 순서로 분석해줘.
```

> [!TIP]
> **핵심 포인트:** AI가 원인을 지레짐작하여 멀쩡한 코드를 덮어쓰는 사고를 막고, 시니어 개발자처럼 여러 가능성을 짚어본 뒤 가장 안전한 코드를 작성하도록 통제합니다.

---

## 🚀 실무 핵심 전략: 바이브 코딩을 위한 3가지 무기

### 🏷️ 1. [구분자와 제약] 마크다운으로 영역 나누고 안전 규칙 걸기
지시문과 데이터가 뒤섞이면 AI는 코드를 제멋대로 생략하거나 없는 라이브러리를 지어냅니다. 마크다운 구분자(`#`, `---`)로 영역을 나누고, "**절대 하지 말아야 할 행동**"을 규칙으로 명시합니다.

#### 📝 [예제 적용 1] 헤더(#, ##)와 네거티브 제약
```text
# 작업 요청
아래 로그인 컴포넌트에 소셜 로그인(구글, 카카오) 버튼을 추가해줘.

## 엄격한 제약 사항
- 코드 생략 금지: "// ...기존 코드..."와 같이 생략하지 말고, 반드시 전체 코드를 온전히 작성할 것
- 임의 패키지 금지: 기존 package.json에 없는 새로운 외부 라이브러리를 임의로 설치하지 말 것
- 추측 금지: 확실하지 않은 API 명세가 있다면 지어내지 말고 주석으로 확인 요청을 남길 것
```

#### 📝 [예제 적용 2] 수평선(---)을 활용한 데이터 블록 분리
````text
아래 회원 데이터에서 최근 30일간 구매 이력이 없는 휴면 회원을 추출하는 스크립트를 작성해줘.

---
## 지켜야 할 규칙
- 결과는 이름과 이메일만 추출할 것
- 날짜 계산 기준은 오늘(현재 시각)로 잡을 것

---
## 회원 데이터
```csv
id,name,email,last_login
1,김철수,chulsoo@example.com,2026-10-15
2,이영희,younghee@example.com,2026-08-01
3,박민수,minsoo@example.com,2026-11-01
```
````

> [!TIP]
> **핵심 포인트:** 지시문과 데이터를 수평선이나 헤더로 격리하고, AI가 자주 저지르는 나쁜 습관(코드 생략, 환각)을 '금지 규칙'으로 틀어막아 프로젝트 환경을 안전하게 보호합니다.

### 📦 2. [출력 제어] 사족 없는 구조화된 출력(JSON) 고정하기
프로그램이나 스크립트와 연동할 때 AI가 "네, 요청하신 데이터입니다!" 같은 인사말을 섞으면 코드 실행 시 에러가 발생합니다. 오직 기계가 파싱할 수 있는 순수 JSON 형식만 반환하도록 강제합니다.

#### 📝 [예제 적용] 파싱 에러 없는 순수 JSON 추출
````text
제공된 고객 문의 내용 2건을 분석해서 의도(Intent)와 긴급도(Urgency)를 분류해줘.

## 출력 형식 규칙
- 인사말이나 부연 설명 없이 오직 순수 JSON 배열만 출력할 것
- 마크다운 백틱(```json) 기호도 포함하지 말고 원시 JSON 문자열만 반환할 것
- 스키마: [{"id": 1, "intent": "환불요청", "urgency": "높음"}]

---
## 분석할 문의 데이터
1. "배송 중 파손되었는데 당장 오늘 안에 교환 안 해주면 소비자원에 신고합니다."
2. "혹시 이 제품 다음 달에 추가 할인 행사 계획이 있나요?"
````

> [!TIP]
> **핵심 포인트:** 불필요한 대화형 사족을 원천 차단하고 스키마(형식)를 지정함으로써, API 통신이나 백엔드 연동에 즉시 사용 가능한 안정적인 데이터를 얻어냅니다.

### 🗺️ 3. [작업 분할] 계획 먼저 세우기(Plan-First)
한 번에 코드를 짜게 하면 중간에 논리가 꼬입니다. 설계(Plan)와 실행(Act) 단계를 물리적으로 분리합니다.

#### 📝 [예제 적용] 2단계 구현 지시
```text
우리 웹사이트에 다크 모드 토글 기능을 추가하려고 해.
바로 코드를 작성하지 말고, 먼저 아래 요구사항을 바탕으로 [작업 계획서]부터 작성해줘. 승인 없이 구현하면 안돼.

---
## 기능 요구사항
- 헤더 우측 상단에 해/달 아이콘 토글 버튼 배치
- 사용자가 선택한 테마를 로컬 스토리지에 저장하여 새로고침해도 유지
- OS(시스템) 다크 모드 설정을 감지하여 기본값으로 자동 반영

## 계획서에 포함할 내용
1. 수정하거나 새로 생성할 파일 목록
2. 테마 상태 관리 및 스타일 적용 흐름
3. 구현 순서(1단계 ➔ 2단계 ➔ 3단계)
```

> [!NOTE]
> 💡 **과거 고급 기법들의 변화**(Step-Back, Self-Consistency 등)  
> 과거 모델에서는 Step-Back(원리부터 설명 유도)이나 Self-Consistency(스스로 다수결 투표) 같은 기교가 쓰였으나, 최신 고성능 모델(GPT-4o, Claude 3.5, Gemini 1.5/2.0)은 내재적 추론 능력이 비약적으로 발전하여 이러한 기법들이 오히려 불필요한 토큰 낭비를 유발합니다. 현재는 "**어떻게 생각할지**"를 강제하기보다 "**명확한 제약과 구조화된 지시**"를 내리는 것이 실무의 핵심입니다.

## 💎 실무 팁: 원하는 결과가 나오지 않을 때의 4가지 점검표

AI가 내 의도와 다른 엉뚱한 답변을 내놓는다면, 복잡한 프레임워크를 외울 필요 없이 아래 4가지만 빠졌는지 확인하면 95% 이상 해결됩니다.

1. **지시**(Instruction)**가 구체적인가?**
   - 나쁜 예: "로그인 페이지 좀 다듬어줘"
   - 좋은 예: "로그인 버튼에 중복 클릭 방지 로직을 추가해줘"
2. **상황**(Context)**을 구체적으로 알려주었는가?**
   - 나쁜 예: "로그인 버튼 컴포넌트 만들어줘"
   - 좋은 예: "Next.js 15 환경이고 Tailwind CSS를 쓰고 있어. 로그인 버튼 컴포넌트 만들어줘"
3. **제약**(Constraints)**을 명확히 걸었는가?**
   - 하지 말아야 할 것(기존 코드 생략 금지, 외부 패키지 임의 설치 금지 등)을 명시했는지 확인
4. **예시**(Example)**를 1줄이라도 보여주었는가?**
   - 말로 길게 설명하는 대신, 원하는 코드 스타일이나 입출력 데이터 형태 예시를 제공했는지 확인

> [!TIP]
> 💡 **프레임워크보다 중요한 기본 뼈대**  
> 시중에 떠도는 수많은 알파벳 프레임워크(RTF, TCREI 등)를 억지로 외울 필요는 없습니다. 상황에 따라 역할(페르소나)이나 출력 형식이 달라질 수 있지만, 실무 프롬프트의 가장 든든한 기본 뼈대는 언제나 "**명확한 지시 + 작업 상황 + 금지 제약 + 입출력 예시**"입니다.
