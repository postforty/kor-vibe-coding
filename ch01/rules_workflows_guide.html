AI 규칙(Rules) & 워크플로우(Workflows) 핵심 가이드

에이전트를 통제하는 두 가지 핵심 축: 항상 지키는 원칙(Rules)과 필요할 때 호출하는 절차(Workflows)를 명확히 분리하여 토큰 비용을 아끼고 개발 정확도를 극대화하세요.

⚡

한눈에 비교: Rules vs Workflows

비교 항목 📜 규칙 (Rules / AGENTS.md) 🚀 워크플로우 (Workflows)
개념 정의 코딩하는 내내 항상 준수해야 하는 상시 제약 조건 특정 시점에 사용자가 호출하는 온디맨드 절차 매뉴얼
적용 시점 매 대화 턴마다 컨텍스트에 상시 자동 포함 채팅창에서 /명령어(예: /commit) 입력 시 로드
토큰 소비 대화가 길어져도 계속 컨텍스트를 차지함 (비용 발생) 호출할 때만 1회성으로 로드되어 평소 토큰 낭비 제로
파일 위치 프로젝트 루트의 AGENTS.md .agents/workflows/<command>.md
대표 예시 버전 고정(Python 3.12), 금지 라이브러리, 보안 수칙, TDD 원칙 깃 커밋 메시지 생성(/commit), 배포, 릴리즈 노트 작성
📜

Section 1. 규칙 (Rules) 설정 가이드

상시 제약 조건

규칙은 에이전트에게 "우리 프로젝트의 법과 행동 규범"을 정해주는 것입니다. 불필요한 시행착오와 코드 리뷰 비용을 획기적으로 줄여줍니다.

📌 1. 버전 및 기술 스택 명시

AI는 레거시부터 최신 문법까지 다 알고 있어 명시하지 않으면 여러 시대의 코드를 혼용합니다.

💬 "파이썬 패키지 관리는 uv를 쓰고 3.12 버전을 기본으로 사용할 것."

🚫 2. 하지 말아야 할 것 (금지 규칙)

AI의 과도한 의욕으로 불필요한 서드파티 패키지가 마구잡이로 설치되는 것을 원천 차단합니다.

💬 "플러터에서 dynamic 타입을 쓰지 마. .env 파일을 하드코딩하지 말 것."

🧪 3. 테스트 및 개발 프로세스 강제

기능 구현 전 테스트 작성을 강제하면 AI가 놓칠 뻔한 잠재적 버그와 엣지 케이스를 자율 해결합니다.

💬 "구현 계획(Plan) 수립 시 백엔드는 반드시 TDD 절차로 단계를 구성할 것."

💡 4. 상식은 빼고 '우리 규칙'만

try-catch 예외 처리, 변수명 짓기 같은 범용 상식은 적지 마세요. 토큰 낭비만 초래합니다.

💬 "이 프로젝트만의 고유 제약 조건만 간결하게 적을 때 준수율이 가장 높음."
실전 템플릿: AGENTS.md 
# 프로젝트 규칙 (AGENTS.md)

## 1. 언어 및 커뮤니케이션
- 모든 답변, 코드 주석, 설명은 반드시 한국어로 작성할 것.

## 2. 개발 환경 및 기술 스택
- Python: 패키지 및 가상환경 관리는 uv를 사용하며, Python 3.12를 기본으로 고정함.
- Frontend: 복잡한 프레임워크 대신 순수 CSS(Vanilla CSS)와 모던 UI 토큰을 사용할 것.

## 3. 금지 규칙 (Never Do)
- API Key, DB 비밀번호 등 민감 정보를 코드에 직접 적지 말 것 (.env 참조 필수).
- .env 및 민감한 설정 파일을 읽거나 답변에 출력하지 말 것.
- 정의되지 않은 외부 라이브러리를 임의로 install하지 말 것.

## 4. 품질 및 테스트 원칙
- 백엔드 비즈니스 로직 작성 시 반드시 TDD(테스트 선작성) 원칙에 따라 단위 테스트를 작성할 것.
🚀

Section 2. 워크플로우 (Workflows) 설정 가이드

온디맨드 절차 작업

워크플로우는 에이전트에게 "슬래시 명령어(/명령어)를 입력했을 때 수행할 정형화된 작업 매뉴얼"입니다.

❓ 왜 커밋 메시지 작성 규칙은 AGENTS.md가 아닌 워크플로우로 만들어야 할까요?
깃 커밋, 배포, 릴리즈 노트 작성 등은 코딩하는 내내 필요한 것이 아니라 작업이 끝난 특정 시점에만 필요합니다. 이를 상시 규칙에 넣어두면 매 턴마다 불필요한 토큰이 낭비되고 에이전트 집중도가 흐려집니다. 워크플로우로 분리하면 평소 토큰 소비가 0이 됩니다!

# 커밋 메시지 생성 워크플로우

## 1. 커밋 컨벤션 기준
- feat: 새로운 기능 추가
- fix: 버그 수정
- docs: 문서 수정
- refactor: 코드 리팩터링 (기능 변화 없음)
- test: 테스트 코드 추가/수정
- chore: 빌드, 패키지 매니저, 환경 설정 변경

## 2. 작동 프로세스
1. 작업 범위 식별: 현재 대화 세션의 히스토리를 분석하여 수정된 작업을 식별합니다.
2. 컨벤션 적용: 위의 커밋 컨벤션 기준을 참고하여 가장 적합한 타입을 선택합니다.
3. 메시지 생성: 제목(Title)과 변경 사항 목록(Body)을 명확한 한국어로 작성합니다.
4. 결과 출력: 사용자가 복사하기 편하도록 반드시 마크다운 코드 블록 안에 담아 출력합니다.
🧭

Section 3. 언제 무엇을 쓸까? (의사결정 기준)

새로운 지침이나 작업을 추가하고 싶을 때, 아래 기준에 따라 저장 위치를 선택하세요:

📜 Rules (AGENTS.md) 에 넣을 것
  • 응답 언어 (한국어 사용 규칙)
  • 개발 언어 및 런타임 버전 (Python 3.12, Node 20)
  • 패키지 매니저 지정 (uv, pnpm)
  • 보안 및 금지 사항 (.env 읽기/노출 금지)
  • 테스트 주도 개발(TDD) 기본 원칙
🚀 Workflows (.agents/workflows/) 로 분리할 것
  • 깃 커밋 메시지 자동 생성 (/commit)
  • 배포 스크립트 실행 및 검증 (/deploy)
  • 코드 리뷰 및 리팩토링 체크리스트 (/review)
  • 기능 완료 후 릴리즈 노트 작성 (/release)
  • 정기 테스트 시나리오 실행 (/test-all)
