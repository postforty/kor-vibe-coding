# 규칙(Rules) 설정 시 주의 사항 핵심 정리

> 규칙 설정 시에는 **'무엇을 할지'**뿐만 아니라 **'어디까지, 어떤 기준으로 행동해야 하는지'**도 함께 정의하는 것이 핵심임.

---

## 1. 버전 및 기술 스택 명시하기
- **이유**: AI 에이전트(안티그래비티)는 과거 방식부터 최신 기술까지 방대한 지식을 보유하고 있어, 규칙이 모호하면 여러 시대의 방식을 혼합하여 코드를 작성할 수 있음.
- **효과**: 사용하는 버전과 개발 방식을 구체적으로 제시하면 현재 프로젝트 환경에 정확히 부합하는 코드만 작성하도록 유도할 수 있음.
- **작성 예시**:
  - `"우리는 파이썬 버전 및 패키지 관리에 uv를 쓰고 3.12 버전을 기본으로 사용해."`
  - `"Node.js는 nvm으로 버전을 관리해 줘."`
  - `"iOS 코드를 작성할 때는 스토리보드 대신 SwiftUI를 사용해 줘."`

## 2. 하지 말아야 할 것(금지 규칙) 명시하기
- **이유**: 에이전트가 지나치게 의욕을 발휘하여 불필요한 라이브러리를 임의 설치하거나 프로젝트에서 쓰지 않는 오래된 방식을 가져올 수 있음.
- **효과**: 금지 규칙을 명확히 적어 두면 불필요한 코드 수정 및 리뷰 비용을 줄이고 코드 품질을 크게 향상시킬 수 있음.
- **작성 예시**:
  - `"플러터에서 'dynamic' 타입을 절대 사용하지 마. 대신 변수에 맞게 타입을 설정해 줘."`
  - `"API Key나 비밀번호를 코드에 직접 적지 말고, 반드시 '.env' 환경 변수를 참조하는 코드로 작성해 줘."`

## 3. 테스트 코드 작성 규칙 명시하기
- **이유**: 기능 코드 작성 시 테스트 코드 작성을 규칙으로 지정하면 에이전트가 놓쳤던 부분을 스스로 인식하여 테스트하고 잠재적 오류까지 고민해 해결함.
- **효과**: 개발 속도와 코드의 안정성을 동시에 확보할 수 있음.
- **작성 예시**:
  - `"구현 계획서(Plan)를 작성할 때 백엔드는 반드시 TDD 절차(테스트 선작성 ➡️ 기능 구현 ➡️ 리팩터링)로 단계를 나누어 계획을 세워 줘."`
  - `"주요 비즈니스 로직을 작성할 때는 단위 테스트 코드를 함께 작성해 줘."`

## 4. 깃 커밋 작성 규칙 명시하기
- **이유**: 커밋 메시지 작성까지 에이전트에게 위임하여 작업 흐름을 원활하게 하고, 여러 작업자가 협업할 때도 일관된 기록을 유지할 수 있음.
- **활용 팁**: 직관적이고 표준화된 **깃모지(gitmoji.dev)** 스타일 규칙을 추가해 두면 협업 시 매우 편리함.
- **작성 예시**:
  - 커밋 메시지 제안 규칙:
    - `✨ Feat: 새로운 기능 추가`
    - `🐛 Fix: 버그 수정`
    - `♻️ Refactor: 코드 리팩터링(기능 변화 없음)`
    - `📝 Docs: 문서 수정`
  - *적용 결과 예시*: `✨ Feat: 로그인 페이지 UI 구현 및 유효성 검사 추가`

---

## 5. 실전 종합 예시 룰 (`AGENTS.md` / 규칙 설정 템플릿)

> **💡 규칙 작성 Tip**: AI가 기본적으로 잘 수행하는 범용 상식(예: 기본적인 try-catch 예외 처리 등)은 굳이 규칙에 넣을 필요 없음. **프로젝트 고유의 제약 조건, 명시하지 않으면 AI가 알 수 없는 환경/버전, 워크플로우(TDD 등)**만 간결하게 작성할 때 규칙 준수율과 효율이 극대화됨.

````markdown
# 프로젝트 규칙 (Rules)

## 1. 언어 및 커뮤니케이션
- 모든 답변 및 코드 주석, 설명은 반드시 **한국어**로 작성할 것.

## 2. 개발 환경 및 패키지 관리
- **Python**: 패키지 및 가상환경 관리는 **uv**를 사용하고, **Python 3.12**를 기본으로 사용할 것.
- **Node.js**: 버전 관리는 **nvm**을 사용할 것.

## 3. 금지 규칙 (하지 말아야 할 것)
- API Key, DB 비밀번호 등 민감 정보를 하드코딩하지 말고 반드시 `.env` 환경 변수를 참조할 것.
- 정의되지 않은 불필요한 외부 라이브러리를 임의로 추가하지 말 것.

## 4. 백엔드 구현 계획서
- 백엔드 기능 개발 계획(Plan)을 수립할 때는 반드시 **TDD(테스트 주도 개발) 원칙**에 따라 작업 단계를 나누어 작성할 것.

## 5. 깃 커밋 규칙
- 커밋 메시지는 프리픽스(Prefix) 컨벤션을 준수하여 제안할 것:
  - `feat:` 새로운 기능 추가
  - `fix:` 버그 수정
  - `refactor:` 코드 리팩터링 (기능 변화 없음)
  - `docs:` 문서 수정
  - `test:` 테스트 코드 추가 및 수정
````
